# STM32 桌面宠物：控制修复与撒娇动作版

基于上传的“桌面宠物代码(2月17日更新)”工程。本版先修复控制与通信逻辑，现有引脚、命令字节、动作角度及 PWM 周期保持兼容。原作者及第三方驱动说明保留在源码中。

## 新动作：撒娇求摸摸

通过蓝牙发送原始字节 `0x50`（十进制 80，ASCII 大写 `P`）触发。串口助手可选择 HEX 模式发送 `50`，不要发送两个文本字符 `50`。两路串口均能解析该字节；现有语音模块要触发它，需在模块侧配置对应输出字节，本版没有修改语音模块词条。

动作名义时长约 4.2 秒：瞪眼并渐变压低身体 → 左右轻倾 → 开心表情、小幅摇尾三次 → 站立。新动作目标腿角为 65–90°，摇尾阶段为 75–105°，每 20 ms 更新一次渐变目标。

渐变依据上次下发的角度，不能测得实际位置；上电尚未下发角度时以 90° 为参考。实际动作形态及行程仍需根据舵机安装和连杆结构确认。正常结束保持之前的尾巴开关状态：之前关闭则回中停止，之前开启则站立后恢复持续摇尾。

新动作指令可中断卖萌，旧动作不再写后续姿态或覆盖新请求；中断到其他动作时由新请求处理器将尾巴回中。再次发送 `0x50` 从当前下发角度重新开始。卖萌期间的 `0x40` 摇尾开关也会接管动作，灯光、调速及未知字节不会使卖萌提前退出。原来的调速命令不改变本动作固定的节奏。

## 使用

用 Keil µVision 打开根目录 `Project.uvprojx`，使用 ARMCC 5.06 update 5 与 `Keil.STM32F1xx_DFP.2.2.0`，执行 Rebuild。串口仍为 9600、8N1。原始工程配置、标准外设库和启动代码一并提供。

本包不包含新版 HEX；需要在 Keil 中完成编译、链接后生成。当前验证包括主机逻辑测试与 ARM GCC 目标文件编译，尚未完成 ARMCC 全工程构建或实物测试。

## 主要改动

- 串口 ISR 读取一次状态、一次接收寄存器，将字节及来源放入共用队列。禁止在 ISR 中刷新 OLED。
- 接收队列实际容量 63 条；满时丢弃新条目并累计 `Serial_RxOverflow`，保留已接收条目的顺序。两路 ISR 入队时短暂关闭中断并恢复原 PRIMASK，避免嵌套生产者破坏队列。
- 收到 ORE、FE、NE、PE 标记的数据时，以 SR/DR 读取顺序清除错误，丢弃本次数据，分别累计 `Voice_RxErrors` 和 `BlueTooth_RxErrors`；随后继续接收。
- `BlueTooth_Process()` 仅在前台执行，处理一批指令并合并表情刷新；同一表情不重复发送。
- 所有动作等待以名义 1 ms 为间隔处理队列。新动作指令更新请求编号，旧动作立即从下一次处理点返回；重复发送同一动作也会重新开始，旧跳跃不能再覆盖新请求。
- 修复摇尾关闭：再次发送 `0x40` 后尾巴回到 90°；若正在摇尾或卖萌，则转为站立；若身体正在执行其他旧动作，保留该动作。
- 灯光、调速和未知字节不再改变当前运动的持续/有限次数策略。语音动作命令选择有限运动，蓝牙动作命令选择持续运动，既有动作自身的完成策略保持原样。
- 连续运动计数减到 0 后保持为 0，避免无符号下溢；修复 `PetAction.h` 头文件保护宏不匹配。

## 协议与调度约定

原字节表与引脚表见 [原版分析](docs/原版分析.md)。字节指原始值，例如 `0x33` 是前进命令，不是两字符文本 `33`。

队列按入队顺序处理；同一批中有多个动作请求时，最终状态采用最后一个请求。此协议不保证逐个完整执行突发发送的每个动作，也不向发送方返回确认消息。两路同时到达时按实际 ISR 入队顺序处理。

动作保持原有阻塞式结构，通过等待中的服务点响应指令。1 ms 是轮询间隔，不是实测响应时间上限；OLED 整屏传输、中断与处理开销仍会增加延迟。后续若需要稳定任务周期，可再将动作改为定时驱动的状态机。

## 验证

在具有 GCC 的 Linux 环境中运行：

```sh
bash tests/run.sh
```

该测试编译实际 `BlueTooth.c`、`PetAction.c`、`Face_Config.c`、`Servo.c` 和重命名入口的 `main.c`，仅替换硬件边界。覆盖两路指令与来源、未知字节、调速与灯光、接收错误恢复、寄存器单次读取、嵌套接收、队列溢出及回绕、表情刷新、动作抢占、同动作重发、尾巴关闭、正常完成、计数饱和与主循环调度。新动作另检查阶段姿态、渐变步长、三次摇尾、重复触发连续性、尾巴状态保持及各阶段边界的抢占。

安装 ARM GNU 工具链后，可额外编译与本次逻辑有关的五个目标文件：

```sh
bash tests/check_arm.sh
```

如使用非标准工具目录，可设置 `ARM_CC` 为编译器路径、`NEWLIB_INCLUDE` 为 newlib 头文件目录。此检查使用工程真实 STM32/CMSIS 头文件，不替代 Keil 的汇编、链接、Flash/RAM 空间检查。

本次结果：1298 个主机回归场景通过，包含 AddressSanitizer/UndefinedBehaviorSanitizer 检查；5 个 ARM 目标文件编译通过。详情见 [验证记录](docs/验证记录.md)，改动总览见 [交付说明](docs/交付说明.md)。

## 实机验证顺序

1. 在原 Keil 工具链中 Rebuild，检查所有编译和链接结果以及 Flash/RAM 占用，保留生成日志。
2. 检查原有坐下、站立、前后移动、左右转、摇摆、跳跃、打招呼、伸懒腰、后腿拉伸与灯光命令。
3. 在跳跃、摇摆和拉伸期间发送其他姿态指令，再测试重复发送相同指令，观察新请求是否能及时接管。
4. 发送两次 `0x40`，确认关闭后尾巴回中、停止摆动；身体运动中关闭尾巴应保留身体动作。
5. 交替使用蓝牙和语音，检查蓝牙持续行走时的语音灯光、调速及未知字节不会改变行走策略；语音动作请求仍接管运动。
6. 连续发送、两路交错发送并观察诊断计数、表情显示和供电状态；确认实际响应延迟及舵机机械行程。
7. 发送 `0x50`，观察身体压低、左右倾斜、三次摇尾及站立；分别在尾巴开/关状态下触发，检查结束状态。
8. 在卖萌的压低、左右倾斜、摇尾和站立阶段发送其他动作、`0x40` 或再次发送 `0x50`，检查是否及时接管且没有旧动作回写；同时测试灯光与调速功能仍可用。

需要实物侧补充：原理图或实际接线、舵机与 OLED 型号、供电方案，以及最明显的现有故障现象。
